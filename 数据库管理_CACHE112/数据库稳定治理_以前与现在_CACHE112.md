# 数据库稳定治理：以前与现在

## 一、B资料记录的事故基线

资料包记录的生产问题不是“玩家正式数据太多”，而是技术历史、幂等请求缓存和大JSON长期累积。事故观察点包括：

- 数据库曾约434MB，接近470MB阻断线；人工做滚动24小时安全清理后约277MB。
- 5类宗门请求/幂等缓存曾合计约158.84MB。
- 秘境请求约50MB、秘境详细事件约47MB、普通世界事件约27MB、修炼临时效果约20MB、机缘V3约10MB。
- 历史累计统计摘录约293万commit、32.8万rollback、3.07万temp files、约111GB temp I/O、15次deadlock。
- 旧客户端存在多组30/60秒固定空转RPC；历史牌九1秒数据库tick曾达到426,768次调用，当前已关闭，禁止恢复。

这些数字是B资料中的生产统计摘录，用来解释根因和后续验收，不代表执行SQL241后数据库已经自动达到某个数值。

## 二、以前的问题

1. 旧清理规则覆盖不全，新模块追加后没有同步进入容量治理。
2. “按天”维护如果一天只跑一次，实际留存可能接近24—48小时，并不是真正滚动24小时。
3. 部分历史清理思路使用全表窗口排序，数据越大成本越高。
4. 请求/result表可能长期缓存较大的dashboard或JSON结果。
5. 客户端大量30/60秒定时RPC，在玩家什么都没操作时仍持续访问数据库。
6. GM功能多但入口分散，容量、清理、Cron、审计需要来回找。

## 三、现在怎么改

### DBCAP03

- 统一使用数据库权威 `clock_timestamp() - interval '24 hours'` 判断滚动TTL。
- 把宗门请求缓存、秘境请求/详细事件、机缘V3/V4、普通世界事件、过期临时修炼效果、Cron历史纳入治理。
- 运行中、未领取、未展示、有效/永久效果、重大/置顶事件全部保护。
- 宗门普通事件先按月汇总，再删除24小时前普通明细。
- 主清理使用时间索引 + LIMIT + `SKIP LOCKED`，单类单轮最多20000条。
- 改造前B资料确认全局清理每日20:25、BSECT06每日04:35；CACHE112只调整这两个已有Cron，不创建重复任务：全局清理 `25 */6 * * *`，BSECT06维护 `35 */6 * * *`。
- autovacuum继续工作；日常治理不使用VACUUM FULL。

### PERF2

只减“空转”，不降低玩家眼前的流畅度：

- 会话空闲心跳：30秒 → 5分钟。
- 修炼本地显示：250ms保持；云端安全同步改10分钟，进入修炼页超过2分钟未同步会立即补一次。
- 机缘本地倒计时：1秒保持；正常按 `next_available_at` 精确到期触发，10分钟仅作异常兜底。
- 天机通知：60秒 → 5分钟兜底。
- 天道余额：5分钟全局 → 修炼页按需 + 30分钟兜底。
- 市场：30秒 → 可见页面90秒兜底；买卖操作仍立即刷新，Realtime保留。
- 世界事件：60秒 → 5分钟兜底；进入页面缓存超过1分钟立即刷新。
- 登录、恢复前台、主动业务操作仍即时同步。
- 牌九Realtime、90/180秒安全重同步、战斗、秘境边界计时、宗门可见体验不动。

B资料的理论估算是固定空闲RPC从约8928次/日降至约600—800次/日，再加玩家真实操作。上线后要用实际pg_stat_statements验证，不把理论值当生产实测值。

## 四、管理方式现在的变化

ADMIN9 R23把“数据库”变成一个独立的手机管理页：容量、保护项、安全候选、24小时规则、Cron、Top10表、近24小时清理、最近失败记录集中显示。实际操作仍调用旧GM的安全RPC，避免为了新界面再造一套数据库权限面。
