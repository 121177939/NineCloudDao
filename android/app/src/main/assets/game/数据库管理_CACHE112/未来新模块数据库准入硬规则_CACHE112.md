# 未来新模块数据库准入硬规则 CACHE112

本文件把B资料中的准入原则固化为后续开发约束。

1. **先分类后建表**：每张新表必须标明“当前状态 / 永久历史 / 技术历史 / 临时状态”。
2. **Append-only必须有出口**：持续追加表在开发时就要给出TTL、硬上限、汇总/归档和清理RPC，不能等数据库满了再补。
3. **永久资产禁止混进TTL表**：角色、背包、装备、资源、宗门当前状态、弟子、交易中状态等不能因为方便而放在会清理的技术历史结构里。
4. **大JSON要证明必要性**：可重建dashboard、大数组、重复快照不长期缓存。请求幂等表只存完成幂等所需的最小结果。
5. **禁止空转写库**：玩家无操作时不要每30/60秒写数据库。用 `next_due_at`、到期时间、前台恢复、页面进入、业务动作驱动。
6. **Cron低频且唯一**：优先6小时/日级，不创建重复同名/同功能Job；牌九秒级/分钟级数据库Tick永久禁止恢复。
7. **清理可并发**：按索引时间条件选择、LIMIT分批、`SKIP LOCKED`，避免大事务和全表窗口排序。
8. **先保业务再清历史**：processing/running/settling、未领取、未展示、有效/永久效果、重大/置顶事件先写保护条件，再写DELETE。
9. **前端无DELETE业务权限**：管理页面调用审计过的SECURITY DEFINER包装RPC，不能把业务表DELETE直接暴露给浏览器。
10. **100人24小时容量报告**：上线前必须估算新增行数、数据库增量、固定RPC次数、Cron次数和清理后稳态；无法估算的模块不得直接投产。
11. **历史迁移不可改写**：已执行SQL只作为历史，修复用新编号迁移；release_control仅为发布显示，不能取代真实结构门禁。
12. **发布必须可检查**：每个新增数据库模块同时提供升级SQL、制度门禁、只读健康检查要点和回滚/停用策略。
